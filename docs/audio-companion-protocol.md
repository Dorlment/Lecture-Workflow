# Lecture Workflow Audio Companion Protocol v1

This protocol connects the Obsidian plugin to a separately installed local audio helper. Version 1 defines communication only; it does not ship, download, or execute a helper.

## Transport and security

- Default endpoint: `ws://127.0.0.1:43127/v1/audio`.
- Equivalent loopback hosts `localhost` and `[::1]` are allowed on the same port and path.
- The first Windows helper implementation binds IPv4 `127.0.0.1` only. The plugin accepts
  `localhost` and `[::1]` for future cross-platform helpers, but those host spellings are not
  guaranteed to reach the Windows v1 server.
- Remote, LAN, and public addresses are rejected. URL credentials, query strings, and fragments are forbidden.
- The first application message is `HELLO`, which also performs authentication with a temporary pairing token.
- A token is generated by the helper from at least 32 cryptographically random bytes and encoded as unpadded base64url. The plugin only validates the format and keeps it in memory. Helpers must compare tokens in constant time.
- Tokens, control-message bodies, PCM, Base64, and audio content must never be logged or included in user-facing errors.
- JSON control messages are UTF-8 and limited to 32 KiB.
- Binary PCM payloads are limited to 64 KiB per frame.

## Session time

Screenshots and audio share the existing classroom `sessionId` and classroom start time. `START.captureStartOffsetMs` is the classroom-relative offset when the plugin sends `START`.

After accepting `START`, the helper starts a monotonic timer immediately. Capture initialization latency is included in the first frame's `offsetMs`; the timer must not be reset when sampling actually begins. Wall-clock values are metadata only and never control ordering.

Frame `sequence` values are strictly increasing. Frame `offsetMs` values are non-decreasing and refer to the same classroom timeline used by screenshots and future transcript events.

## Target audio format

- signed 16-bit PCM, little-endian (`s16le`)
- 16000 Hz
- mono

The helper may resample the operating system's native format before sending frames.
The Windows helper emits fixed 20 ms frames (320 samples / 640 payload bytes).

## Control messages

Every message contains `protocolVersion: 1`. Receivers reject missing fields, unknown fields, unknown message types, invalid field types, and incompatible versions.

### HELLO / AUTH

The plugin sends this as the first application message after the WebSocket opens.

```json
{
  "type": "HELLO",
  "protocolVersion": 1,
  "sessionId": "20260809-143000-123",
  "clientVersion": "1.0.0",
  "auth": {
    "scheme": "pairing-token",
    "token": "<temporary base64url token>"
  }
}
```

### READY

`READY` confirms successful authentication and capability negotiation.

```json
{
  "type": "READY",
  "protocolVersion": 1,
  "helperVersion": "1.0.0",
  "platform": "windows",
  "supportedSources": ["windows-wasapi-loopback"],
  "supportedFormats": [{ "sampleFormat": "s16le", "sampleRate": 16000, "channels": 1 }],
  "capabilities": ["audio-frame-v1", "heartbeat-v1", "source-selection-v1"]
}
```

Reserved source values are:

- `windows-wasapi-loopback`
- `macos-screencapturekit`
- `linux-pipewire`
- `microphone-input`

### START

```json
{
  "type": "START",
  "protocolVersion": 1,
  "sessionId": "20260809-143000-123",
  "sourceId": "windows-wasapi-loopback",
  "format": { "sampleFormat": "s16le", "sampleRate": 16000, "channels": 1 },
  "sessionStartedAtUnixMs": 1786257000123,
  "captureStartOffsetMs": 12500
}
```

`sessionStartedAtUnixMs` is diagnostic metadata. `captureStartOffsetMs` plus helper monotonic elapsed time is authoritative.

The Windows helper records its monotonic start timestamp immediately after accepting a valid
`START`. It records each WASAPI batch timestamp inside the capture callback and subtracts the
batch duration to estimate the first captured sample. Capture initialization time is therefore
included. After the first frame, the wire offset is the greater of that capture estimate and the
previous offset plus 20 ms; a real pause may create a larger jump.

### STATUS

`status` is one of `connecting`, `ready`, `capturing`, `stopped`, or `error`. Binary frames are valid only after `STATUS capturing`.

### STOP

The plugin sends `STOP` with the current `sessionId`. The helper releases capture resources and acknowledges with `STATUS stopped`.
The WebSocket remains authenticated and ready after a normal STOP, so the same connection may
send another START. A new capture resets its wire sequence to zero.

### ERROR

`ERROR` contains a stable `code`, a short safe Chinese `messageZh`, and `retryable`. Codes in v1 are `AUTH_FAILED`, `PROTOCOL_MISMATCH`, `INVALID_REQUEST`, `SOURCE_UNAVAILABLE`, `FORMAT_UNSUPPORTED`, `CAPTURE_FAILED`, `BUSY`, and `INTERNAL_ERROR`.

The plugin maps codes to local safe messages and does not display or log the complete remote response.

### PING / PONG

Either peer may send `PING` with a non-negative integer `id`. The receiver replies with `PONG` carrying the same `id`.

## AUDIO_FRAME binary layout

The 32-byte header and payload use little-endian byte order.

| Offset | Size | Field |
| --- | ---: | --- |
| 0 | 4 | ASCII magic `LWAF` |
| 4 | 1 | frame version (`1`) |
| 5 | 1 | sample format (`1` = s16le) |
| 6 | 1 | channels (`1`) |
| 7 | 1 | flags/reserved (`0`) |
| 8 | 4 | `sequence`, uint32 |
| 12 | 4 | `sampleRate`, uint32 (`16000`) |
| 16 | 4 | `sampleCount`, uint32 |
| 20 | 4 | `payloadLength`, uint32 |
| 24 | 8 | `offsetMs`, uint64 |
| 32 | variable | PCM payload |

`durationMs` is never transmitted. A receiver derives it as `sampleCount / sampleRate * 1000`.

The receiver first parses `offsetMs` as `BigInt` and rejects values greater than `Number.MAX_SAFE_INTEGER` before converting to `number`. It also requires:

- `payloadLength <= 65536`;
- `payloadLength` exactly equals the received bytes after the header;
- `payloadLength === sampleCount * channels * 2` for s16le;
- a compatible frame version and target format;
- strictly increasing `sequence` and non-decreasing `offsetMs`;
- client state already equal to `capturing`.

## Client lifecycle

The plugin state machine is `idle → connecting → authenticating → ready → capturing → stopping → ready`, with terminal/recoverable `disconnected` and `error` states. It uses bounded connection, authentication, heartbeat, and stop timeouts. There is no automatic reconnect, paid request, microphone fallback, or provider switching.

Disconnect or failure clears sockets, timers, callbacks, and frame counters. The runtime-only pairing token is retained solely for an explicit user-initiated retry; it is never persisted and is cleared by `clearConfiguration()` or plugin disposal. The plugin never reconnects automatically and never stores or uploads audio in protocol v1.
