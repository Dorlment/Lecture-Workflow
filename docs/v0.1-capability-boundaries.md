# Lecture Workflow V0.1 能力边界

本文档基于 V0.1 实际代码配置与已完成的人工 Benchmark 整理，用于描述当前版本**已经验证**的能力范围和**尚未建立**的边界。

注意：除标注为「硬限制」的项目外，其余数字均为有限次数人工实测结果，不构成 SLA 或保证。

## 1. V0.1 当前支持的完整课堂流程

课堂监听 → 系统音频采集（Audio Companion）→ Realtime ASR → 原始文字稿自动持久化（`## 原始文字稿`，含 `[HH:MM:SS]` 时间戳）→ 课堂截图（写入 `## ⏱课堂时间线`）→ 截图与 transcript 共享单调递增课堂时间轴（STOP/START 跨 run 连续）→ AI 结构化整理：

- 无图片（text-only）：完整原始文字稿 + timelineContext → Text Provider（如 DeepSeek）→ 最终结构化 Markdown
- 有图片（vision）：课堂截图（经时间轴筛选）→ Qwen-VL 生成视觉证据 → 完整原始文字稿 + timelineContext + 视觉证据 → Text Provider 生成最终结构化 Markdown

→ 预览确认 → 冲突保护写入 Vault。

## 2. 硬限制（代码强制）

| 项目 | 值 | 代码位置 |
|---|---|---|
| Text Provider 单次输出 token 上限 | 8192 | `ai-generation.ts` `STRUCTURE_MAX_OUTPUT_TOKENS` |
| Qwen-VL 视觉证据输出 token 上限 | 2048 | `vision-generation.ts` evidence 调用 `maxTokens: 2048` |
| 图片数量硬上限 | 10 | `vision-limits.ts` `MAX_VISION_IMAGE_COUNT` |
| 设置页图片数量可调范围 | 1–10 | `settings-data.ts` `normalizeVisionImageCount` clamp |
| 请求超时（默认，可调） | 150 秒 | `settings-data.ts` `requestTimeoutMs: 150_000` |

超出图片硬上限时：经 `selectImagesByTimeline()` 按时间轴保留首尾 + 中间均匀采样，不会静默截断语义之外的失败。

## 3. 当前 retry / repair 行为

- **无自动网络重试**。每次「发送并整理」最多调用：
  - text-only：Text Provider 1 次；若结构校验失败且 finishReason 正常，追加 1 次格式修复（共最多 2 次）
  - vision：Qwen-VL 恰好 1 次 + Text Provider 最多 2 次（生成 + 修复）
- `finishReason = length`（触及 8192 输出上限）时**不触发 repair、不自动重试**，直接返回「不完整」结果：预览可见、可复制，但禁止写入 Vault。
- repair 仍未通过校验时同样返回不完整结果，不会无限循环。

## 4. 人工 Benchmark 实测（4 例，均 finishReason=stop、attempts=1、isComplete=true）

| Case | transcriptChars | 估算 input tokens* | 截图（源/选中） | Qwen-VL 耗时 | Text 耗时 | 总耗时 |
|---|---|---|---|---|---|---|
| A | ≈20,327 | ≈10,164 | 6 / 6 | ≈17s | ≈21s | ≈38s |
| B | ≈11,933 | ≈5,967 | 4 / 4 | ≈9s | ≈22s | ≈31s |
| C | ≈6,233 | ≈3,117 | 3 / 3 | ≈7s | ≈64s | ≈72s |
| D | 7,297 | 3,649 | 3 / 3 | ≈18s | ≈61s | ≈79s |

\* 估算口径为 `ceil(字符数 / 2)` 的粗略近似，**不是**模型真实 tokenizer 计数。

结论性表述：

- 当前人工验证约 **2 万字符 transcript + 6 张截图**可一次成功完成整理，但**尚未建立严格最大输入长度边界**。
- 实测总耗时范围约 **31–79 秒**。这只是当前实测范围，不能承诺固定完成时间。
- Provider 延迟存在明显波动：较短的 transcript（Case C/D）Text Provider 耗时反而超过 60 秒，说明耗时主要由服务端排队/负载决定，不能按 transcript 长度线性预估。

## 5. finishReason = length 的含义与用户影响

- 含义：模型输出达到 8192 output-token 上限被截断，**不是**输入超限，也不是网络错误。
- 真人测试中出现过一次 length，同类课程重新生成后恢复为 stop。更合理的解释是该次输出恰好触及输出上限（模型输出长度存在自然波动），不应简单归因于 API 拥挤。
- 用户影响：预览中可以看到不完整结果并手动复制，但**无法写入 Vault**；需要重新整理，或缩短文字稿后再整理。

## 6. 当前不存在的边界

- **没有插件侧的输入/context token 预检**：发送前不检查 transcript 长度或估算 token 数；输入超出模型上下文时依赖服务端报错映射（`context-limit` 错误提示），不会静默截断。
- **没有严格「最大文字稿字符数」**：代码中不存在该常量。可整理上限由「模型上下文窗口」与「8192 输出预算是否够覆盖笔记长度」共同决定，目前只有实测点，没有推导出的公式。

## 7. 推荐使用范围

基于当前实测，以下场景信心较高：

- 单节课堂（约 1–2 小时）规模的实时转写整理
- transcript 约 2 万字符以内
- 课堂截图 10 张以内（默认全选，无需筛选）

超出此范围不代表一定失败，只是尚未验证。

## 8. 已知风险

- **长课程输出截断**：课程内容越多，最终笔记越接近 8192 输出预算，length 概率上升；一旦发生只能人工重试，且重试不保证成功。
- **耗时不可预期**：Provider 延迟波动大（31–79 秒实测），超时上限 150 秒在极端拥塞下可能不足。
- **token 估算粗糙**：benchmark 中的 estimatedInputTokens 只是 chars/2 近似，不能用于精确预检。
- **视觉证据丢失风险**：Qwen-VL evidence 上限 2048 token，图片多且内容复杂时证据可能被压缩，最终笔记丢失部分视觉细节（尚未实测到该边界）。

## 9. 超出能力边界后的建议行为

- finishReason = length：在预览中复制已生成内容，或重新执行整理；若反复 length，可尝试缩短原始文字稿（删除无关段落）后重试。
- 超时（150 秒）：检查网络后在设置页调大请求超时，或稍后重试。
- context-limit 报错：当前版本不会静默截断输入；请手动缩短文字稿。
- 图片超过 10 张：插件按时间轴自动筛选至上限；如需更多图片参与，只能分批整理（V0.1 未提供）。

## 10. V0.1 不支持 / 暂不保证的场景

- 超长课程（transcript 远超 2 万字符）的一次性完整整理
- 输出长度超过 8192 token 的超详细笔记
- 图片超过 10 张且全部参与整理
- 断网/Provider 故障后的自动恢复续跑
- 任何固定完成时间承诺
- 数据库、云同步、录音保存、跨设备恢复

## 11. V0.2 可考虑的方向

- **输出 continuation**：length 截断时以「继续」方式续写剩余笔记，而非整体重试
- **transcript chunking / Map-Reduce**：分段整理后合并，突破单次上下文与输出预算
- **token preflight**：发送前估算输入规模，提前提示风险而非事后报错（需更可靠的估算口径或 tokenizer）
- **自适应输出预算**：按 transcript 规模在服务端允许范围内调整 max_tokens
- **Benchmark 数据累积**：结构化 diagnostics 仍保留在生成结果与预览数据中，后续可由明确的开发验证入口导出；正式 bundle 默认不向 console 输出 benchmark 日志
